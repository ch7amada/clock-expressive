# Review F04 (round 1)
Verdict: CHANGES_REQUESTED
## Findings
1. [BLOCKER] app/src/main/kotlin/org/fossify/clock/ui/navigation/ClockApp.kt:82-97,99-100 — the `tabRequests` `LaunchedEffect(Unit)` (lines 97-101) captures the `navigateToTab` lambda from the **first composition** (line 82), which closes over that composition's `selectedTab` (the start tab). Every subsequent intent tab request is compared against this stale start tab. Concretely: with `defaultTab = TAB_ALARM`, the app starts on Alarm (stale `selectedTab` = ALARM), the user taps Clock, then an alarm notification taps in with `OPEN_TAB = TAB_ALARM` (emitted by `Context.kt:236` / `SplashActivity.kt:12`) — the guard `tab != selectedTab` (line 83) evaluates to false and the navigation is skipped, so the requested tab is never shown. The main flow works only by coincidence (request ≠ start tab). This violates "shortcuts, intents (OPEN_TAB, TOGGLE_STOPWATCH, TIMER_ID) … still work" (the alarm-notification→alarm-tab path is a core Fossify behaviour). Required change: compute the current tab fresh from the back-stack state inside the collector instead of calling the captured lambda, e.g.:
   ```kotlin
   LaunchedEffect(Unit) {
       tabRequests.collect { tab ->
           val current = ClockTab.fromNavRoute(backStackEntry.value?.destination?.route) ?: startTab
           if (tab == current) return@collect
           hapticFeedback.performHapticFeedback(HapticFeedbackType.SegmentTick)
           onTabChanged(tab)
           navController.navigate(tab.route()) {
               popUpTo(navController.graph.findStartDestination().id) { saveState = true }
               launchSingleTop = true
               restoreState = true
           }
       }
   }
   ```
   (The UI-click paths at lines 112/139 are unaffected — their lambdas are recreated on every recomposition.)
2. [MINOR] app/src/main/kotlin/org/fossify/clock/ui/navigation/ClockApp.kt:122 — in the wide layout the NavHost content gets `.navigationBarsPadding()` (all system bars), and the inner `TabPlaceholder` app bar independently applies `TopAppBarDefaults.windowInsets` (Horizontal+Top, see `AppBar.kt:1528, 2751`). Net result: the wide-window top app bar renders one status-bar height below the screen top, so it does **not** extend behind the status bar (unlike the phone branch, where the inner Scaffold starts at y=0 and the app-bar surface covers the status-bar band), and the status-bar band shows window `background` instead of the app-bar `surface`. Fix: pad only the bars the content slot itself must avoid, i.e. replace `.navigationBarsPadding()` with `.windowInsetsPadding(WindowInsets.systemBarsForVisualComponents.only(WindowInsetsSides.Horizontal + WindowInsetsSides.Bottom))` so the app bar spans behind the status bar like on phones while the content still avoids the home indicator.
